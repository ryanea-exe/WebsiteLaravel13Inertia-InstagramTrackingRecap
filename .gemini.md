# Gemini Agent Instructions — Instagram Employee Engagement Tracking

## 1. Read Documentation First

Before changing code, read:

```text
.docs/PRD.md
.docs/ARCHITECTURE.md
.docs/DATABASE.md
.docs/TASKS.md
```

Then inspect the existing Laravel project structure.

## 2. Root Project Rule

**IMPORTANT: `my-project` is the Laravel root project.**

Never create a nested Laravel source folder such as:

```text
my-project/src/
```

The standard Laravel folders live directly under `my-project`:

```text
my-project/app
my-project/bootstrap
my-project/config
my-project/database
my-project/public
my-project/resources
my-project/routes
my-project/storage
my-project/tests
```

React/TypeScript belongs under:

```text
my-project/resources/js/
```

Do not move Laravel source into `src`.

## 3. Development Workflow

Work phase-by-phase according to `.docs/TASKS.md`.

Before coding:
1. identify current phase;
2. inspect existing files;
3. read relevant documentation;
4. state the intended changes;
5. implement only the requested phase.

Do not jump to later phases unless explicitly requested.

## 4. API Rules

Instagram/Meta API capability must be based on official documentation.

Never invent:
- endpoint;
- permission/scope;
- response field;
- metric;
- user-level engagement capability.

Never use:
- scraping;
- private endpoints;
- browser automation to imitate Instagram;
- Instagram passwords.

If a requested feature depends on unavailable official API data, stop and explain the limitation.

## 5. Identity Rules

Use Instagram User ID as the stable identity.

Username is mutable.

Never create a new employee merely because the username changed.

Comment matching:

```text
commenter_instagram_user_id
=
employee.instagram_user_id
```

## 6. Data Integrity

Sync must be idempotent.

Use external IDs and database unique constraints.

Media:
```text
external_media_id UNIQUE
```

Comment:
```text
external_comment_id UNIQUE
```

Do not duplicate records when sync runs multiple times.

## 7. Security

- never expose access tokens;
- encrypt stored access tokens;
- never log tokens;
- validate all input;
- use Laravel authorization;
- use `.env` for secrets;
- do not commit secrets.

## 8. Laravel Architecture

Controllers should be thin.

Prefer:

```text
Controller
  ↓
Action / Service
  ↓
Model / Repository-like query
  ↓
Database
```

API integration:

```text
Controller/Job
  ↓
Instagram Service
  ↓
Instagram Client
  ↓
Official API
```

Heavy synchronization belongs in Jobs/Queue.

## 9. Database

Migrations are the source of truth.

Do not manually edit production tables as a substitute for migrations.

When changing schema:
1. create migration;
2. update model;
3. update related code;
4. update `.docs/DATABASE.md`;
5. test migration.

## 10. Reporting Rules

A media belongs to a reporting period when:

```text
published_at >= start_at
AND
published_at <= end_at
```

Timezone must be handled consistently.

Do not accidentally mix local timezone boundaries with UTC timestamps.

## 11. Metrics

Aggregate metrics and user-level activity are different.

Example:

```text
likes = aggregate media metric
comments = aggregate media metric
```

A media having 100 likes does not mean the system knows the 100 users who liked it.

Only claim employee-level activity when the API provides the required user identity.

## 12. Testing Requirements

Test at least:
- empty response;
- normal response;
- pagination;
- duplicate sync;
- API error;
- rate limit;
- period boundary;
- username change;
- employee matching;
- authorization.

## 13. Frontend

Use:
- React;
- TypeScript;
- Inertia;
- Tailwind.

Prefer reusable components.

Use clear Indonesian UI labels.

Do not hard-code API secrets into frontend code.

## 14. Code Quality

Prefer:
- clear naming;
- small services;
- typed frontend props;
- Form Requests for validation;
- Policies for authorization;
- Jobs for asynchronous work;
- explicit database constraints.

Avoid:
- giant controllers;
- duplicated API code;
- magic strings where constants/enums are appropriate;
- unvalidated request data;
- unnecessary abstractions.

## 15. Agent Stop Conditions

Stop instead of guessing if:
- API capability is uncertain;
- existing schema conflicts with requested schema;
- authentication architecture is unclear;
- an external API requires a permission that has not been verified;
- a requested user-level metric cannot be supported by the official API.

## 16. Definition of Done

Before marking a task complete:
- code is implemented;
- relevant tests pass;
- migration is valid;
- no secret is exposed;
- documentation remains consistent;
- project runs from `my-project`;
- no `my-project/src` wrapper was introduced.
